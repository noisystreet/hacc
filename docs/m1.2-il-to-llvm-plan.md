# M1.2 方案：EDG IL → LLVM IR

> 状态：**调研完成，方案待评审**（2026-10）。
> 上游：[compiler-implementation-plan.md](compiler-implementation-plan.md) §5.2（集成形态）、§6.1（设备端）、§6.3（衔接点）。
> 前置：M1.1 已打通「LLVM IR → PTX」（`coolicc` 接入 LLVM/NVPTX，见 CHANGELOG）。
> 相关：[ADR 0002](adr/0002-llvm-nvptx-device-backend.md)、[ADR 0003](adr/0003-host-stub-fatbin-registration.md)、
> [tools/il_spike/README.md](../tools/il_spike/README.md)、[tools/il_spike/cuda-attributes.md](../tools/il_spike/cuda-attributes.md)。

## 1. 目标与范围

**目标**：把 `coolfe++` 产出的 **EDG IL** 翻译为 **LLVM IR**，交给 M1.1 的 NVPTX 后端发射 PTX。

**M1.2 范围（最小切片）**：

- 内核形态：**无参 / 标量参**的 `__global__` 函数。
- 必须支持：内建维度变量（`threadIdx`/`blockIdx`/`blockDim`/`gridDim`）、`__syncthreads()`。
- 产物：LLVM IR（文本或内存 Module），供 `coolicc` 消费。

**不在 M1.2 范围**：`__shared__`/`__constant__`（M3）、向量类型（M3）、原子/`__threadfence`（M4）、
主机桩与 `<<<>>>`（M2）、cubin/`ptxas`（M6）。

## 2. 调研结论（EDG IL 是什么）

依据 EDG 官方文档（`doc/source/il.rst`、`lower_il.rst`、`int_overview.rst`、`ext_intf.rst`、`trans_unit.rst`）：

### 2.1 IL 是**内存中的树**，不是文本格式

- IL 是**内存数据结构**（`il_def.h` 定义全部表项），**不是**稳定的文本/二进制契约。
- 官方明确：「IL 数据结构是前端传给后端的**唯一**信息，没有额外隐藏信息」。
- 表项以 `a_*`（结构体）/ `an_*` / `iek_*`（entry kind）命名；表达式节点 `an_expr_node`（`enk_*`/`eok_*`），
  语句 `a_statement`（`stmk_*`），类型 `a_type`（`tk_*`），常量 `a_constant`（`ck_*`）。

### 2.2 两级 memory region

- **file scope region**（常驻）+ **每个顶层函数一个 function scope region**（同一时刻只保证一个在内存）。
- 指针规则：function scope 内的表项**只能被本 region 内**指向；跨 region 引用必须放 file scope。
- 因此**函数接口描述在 file scope，函数体在 function scope**。

### 2.3 三种前后端连接方式（官方列出）

| 方式 | 说明 | 内存 | 速度 |
| --- | --- | --- | --- |
| **① 内存直传** | 整棵 IL 树在内存中交给后端 | 最高 | 最快 |
| **② IL 文件往返** | 按顶层函数写文件、后端按需读回 | 最低 | 最慢 |
| **③ 逐函数翻译后丢弃** | 后端把 IL 翻成自己的 IR，随即丢弃原 IL | 中 | 中 |

> 官方原话：方式 ③ 即「把 IL 翻译成后端使用的另一种中间语言，然后丢弃原 IL」——**这正是 hacc 要做的**。

### 2.4 IL 文件与工具

- IL 可写文件（`il_write.c` / `il_file.h`）、读回（`il_read.c` / `il_read.h`）、人类可读显示（`il_display.c`）。
- 工具：`cpfe`（前端）、`cdisp`（显示 IL）、`eccp`（驱动脚本）。
- **已知问题**：`cdisp` 对含任意 `__attribute__` 的二进制 IL 会断言崩溃（EDG 上游 bug，见 spike README）；
  但 `--il_display` 落盘可正常检索，**不影响 hacc**。

### 2.5 属性（A2 决策 (a) 的落点）

- 属性是 IL 一等公民：`file-scope attribute@…` 实体，字段含 `kind`/`family`/`name`/`arguments`/`group`。
- 声明实体经 `source_corresp.attributes:` **指向**属性实体。
- 开启 `RECORD_UNRECOGNIZED_ATTRIBUTES` 后，CUDA 限定符（`cool_global` 等）以 `kind: unrecognized` 进入 IL。
- **消费方式**：`coolicc` 按属性 `name` 字符串匹配（契约见 `cuda-attributes.md`）。

### 2.6 关键约束（对 hacc 的影响）

1. **IL 无稳定文本契约** → 不能像「读 JSON」那样解析；必须**链接 EDG 前端库**用其 API 遍历 IL 树。
2. **IL 是 C++ 超集** → 未降级 IL 含模板/重载等；一期子集简单，但仍需处理 C++ 语义（如 `extern "C"` 链接）。
3. **memory region 规则** → 遍历时须遵守「function scope 指针不外泄」；跨函数引用走 file scope。
4. **EDG 不做优化** → IL 是「高层、贴近源码」的树，翻译到 LLVM IR 需自己做**语义降级**（如 `<<<>>>` 已由 coolfe++ 改写）。

## 3. 方案选型

### 3.1 三种候选

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 链接 EDG 前端库，内存遍历 IL** | `coolicc` 链接 EDG 前端库，用 `il_read`/`il_walk` 读 IL 树，直接建 LLVM IR | 官方推荐路径；无文本往返；信息最全 | 与 EDG 库强耦合；需摸清 `il_def.h` 全部表项 |
| **B. 解析 `--il_display` 文本** | 解析人类可读 IL 文本 | 松耦合、易调试 | 文本非契约、易随版本变；信息可能丢失；脆弱 |
| **C. 用 EDG 的 C 生成后端（`c_gen_be`）产 C，再喂 clang** | 借 EDG 产 C，clang 产 IR | 复用成熟后端 | 引入 clang 依赖；C 往返丢信息；违背 ADR 0002「不依赖 nvcc/clang 前端」取向 |

### 3.2 推荐：**方案 A（链接 EDG 前端库，内存遍历 IL）**

理由：

1. **官方路径**：EDG 文档明确「IL 树是前后端唯一接口」，方式 ③（逐函数翻译后丢弃）就是为 hacc 这类后端设计的。
2. **信息完整**：内存树含全部字段（属性、类型、source_corresp），无文本往返损耗。
3. **与阶段 A 兼容**：阶段 A 的「IL 文件」是**进程隔离**手段——`coolfe++` 写 IL 文件，`coolicc` 读回。
   两者都链接 EDG 库（`il_write` / `il_read`），**接口仍是 IL 文件**，符合 §5.2 阶段 A 定义。
4. **不违背 ADR**：ADR 0002 定「EDG AST/IL → LLVM IR」，方案 A 正是此路径。

> **澄清**：阶段 A 的「IL 文件接口」≠「解析 IL 文本」。IL 文件是 EDG 的**二进制 IL 格式**（`il_file.h`），
> 由 `il_read` 读回成内存树。hacc 消费的是**内存树**，不是文本。

### 3.3 与阶段 B 的关系

- 阶段 A（本方案）：`coolfe++` 写 IL 文件 → `coolicc` 读回 → 遍历建 IR。**进程隔离**。
- 阶段 B（延后）：`coolfe++` 链接前端库，实现后端回调，**单进程**直接建 IR。
- 两者**共用**「IL 树 → LLVM IR」的翻译核心（本方案的第 4 节），阶段 B 只是换「IL 从哪来」。

## 4. 翻译核心设计（IL 树 → LLVM IR）

### 4.1 总体结构

```
coolicc:
  il_read(IL 文件) ──▶ IL 内存树
                        │
                        ▼
              ┌─────────────────────┐
              │  IlToLlvmTranslator │  ← 本方案核心
              │  (遍历 IL 树)        │
              └─────────────────────┘
                        │
                        ▼
                  llvm::Module ──▶ (M1.1) NVPTX 后端 ──▶ PTX
```

### 4.2 遍历策略

- **入口**：file scope region 的声明列表（routines / types / variables）。
- **筛选**：只处理带 `cool_global` 属性的 routine（内核）；`cool_device` 函数（M3+）。
- **逐函数**：对每个内核，进入其 function scope region，遍历函数体语句树。
- **遵守 region 规则**：function scope 指针不外泄；跨函数引用经 file scope 的 routine 接口。

### 4.3 映射表（IL → LLVM IR）

| IL 概念 | LLVM IR |
| --- | --- |
| `a_routine`（内核） | `Function`，调用约定 `ptx_kernel`，属性 `nvptx-kernel` |
| 内核名 | 按 B2 规则（`extern "C"` 原名 / `_hacc_k_` + Itanium） |
| 参数（标量） | 函数参数（`param` 地址空间，按 CUDA 参数 ABI） |
| `a_type`（标量） | `i32`/`i64`/`float`/`double` 等 |
| `a_statement`（`stmk_*`） | LLVM `BasicBlock` + 指令 |
| `an_expr_node`（`eok_*`） | LLVM 指令（算术/比较/调用/转换） |
| `threadIdx.x` 等内建 | `llvm.nvvm.read.ptx.sreg.tid.x` 等 intrinsic |
| `__syncthreads()` 调用 | `llvm.nvvm.barrier0` |
| `cool_shared` 变量（M3） | `addrspace(3)` 全局 |
| `cool_constant` 变量（M3） | `addrspace(4)` 全局 |

### 4.4 内建变量与函数的识别

- **内建变量**（`threadIdx`/`blockIdx`/`blockDim`/`gridDim`）：由 `coolfe++` 随附头声明为
  `extern` 全局（见 spike 探针 `kernel_probe.cpp`）；`coolicc` 按**名字**识别，映射到 NVVM intrinsic。
- **`__syncthreads()`**：IL 中是普通 routine 调用；`coolicc` 按**被调函数名**识别，映射 `llvm.nvvm.barrier0`。
- **契约**：内建名清单固定（见 `cuda-attributes.md` §5），`coolfe++` 与 `coolicc` 对齐。

### 4.5 属性消费

- 遍历 routine 时读 `source_corresp.attributes:` → 属性实体 → `name` 字段。
- 按 `cuda-attributes.md` 的清单匹配：`cool_global` → 内核；`cool_device` → 设备函数；等。
- **一期只依赖 `name` 字符串**（A2 决策 (a)）；升级到 (b) 后改按 `kind` 匹配。

## 5. 分步实施（建议）

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| **M1.2.0** | 打通 `coolfe++`：`.cu` → EDG IL 文件（复用 spike 的 `cpfe` 调用） | 产出 IL 文件 |
| **M1.2.1** | `coolicc` 链接 EDG 库，`il_read` 读回 IL，**打印** file scope 的 routine 列表 | 能列出内核名 |
| **M1.2.2** | 遍历最小内核（无参）的 function scope，建空 `Function`（`ptx_kernel`） | 产出 `.visible .entry` |
| **M1.2.3** | 支持标量参数 + 简单语句（赋值/算术/`if`） | golden PTX 比对 |
| **M1.2.4** | 内建变量（`threadIdx` 等）+ `__syncthreads()` | golden PTX 比对 |
| **M1.2.5** | 端到端：`.cu` → PTX（`hacc` driver 编排） | e2e 测试 |

> 每步都应有 golden 测试（`.cu` → 期望 PTX 片段），与 M1.1 的 `golden_device_empty_kernel` 同风格。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| **EDG IL API 复杂**（`il_def.h` 表项繁多） | 高 | 只实现子集所需表项；以最小内核起步，逐格扩展；对照 EDG 文档与源码 |
| **EDG 库链接/构建复杂** | 中 | 复用 `fetch_edg.sh` 的构建产物；`HACC_WITH_EDG` 开关隔离；无 EDG 时骨架仍可构建 |
| **IL 版本漂移**（IL 非稳定契约） | 中 | 固定 EDG commit（ADR 0005）；升级时回归 golden |
| **memory region 指针规则** | 中 | 严格遵守「function scope 指针不外泄」；跨函数引用走 file scope |
| **C++ 语义降级**（重载/模板） | 中 | 一期子集简单；`extern "C"` 内核为主；复杂特性延后 |
| **内建名契约漂移** | 低 | 清单固定于 `cuda-attributes.md`；`coolfe++`/`coolicc` 同步 |

## 7. 待拍板问题

1. **`coolicc` 是否直接链接 EDG 前端库？**（方案 A 的前提）
   - 是：需 `HACC_WITH_EDG` 开关 + EDG 构建产物；`coolicc` 体积增大。
   - 否：退回方案 B（解析文本），脆弱。
   - **建议：是**（方案 A）。
2. **IL 文件格式**：用 EDG 二进制 IL（`il_write`/`il_read`）还是 `--il_display` 文本？
   - **建议：二进制 IL**（官方契约、信息完整）；文本仅用于调试。
3. **翻译核心的归属**：放在 `coolicc` 内，还是独立库（`src/device/il_to_llvm/`）？
   - **建议：独立库**，便于阶段 B 复用与单元测试。
